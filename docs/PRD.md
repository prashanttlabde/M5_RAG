# PRD: Review Pulse for ChatGPT

**Owner:** Prashant Labade  |  **Status:** Draft v1  |  **Assignment:** RAGs and Context Engineering (NextLeap PM Fellowship)
**Product under study:** ChatGPT mobile app, India (Google Play), same product as Milestone 1 (voice-based chat diagnosis)

---

## 1. Problem

Thousands of reviews arrive every week. Product teams cannot read them all, so they miss trends. Support teams answer the same fee question over and over because there is no single, trusted explanation. Manual analysis is slow; naive AI analysis is risky because LLMs miscount, paraphrase quotes and state fee facts from stale memory.

## 2. Users

| User | Need | Pain today |
|---|---|---|
| Product manager (primary) | A one-minute weekly read on what is going wrong | Reads a handful of reviews, anecdote-driven |
| Support lead | A standard, correct explanation of a confusing charge | Agents improvise, answers differ |
| Reviewer / approver | Confidence that nothing goes out unchecked | Fear of AI writing or sending unreviewed content |

## 3. Goals and non-goals

**Goals**
- G1: Turn 8-12 weeks of public reviews into at most 5 themes, a ranked top 3, 3 verbatim quotes and 1 recurring fee confusion.
- G2: Produce a weekly product pulse (at most 250 words) and a fee explainer (at most 6 bullets, 2 official links, Last checked date).
- G3: Publish both through MCP tools (Google Doc append, Gmail draft) only after explicit human approval.
- G4: Make every number and quote verifiable.

**Non-goals:** auto-sending email, scraping private data, sentiment dashboards, multi-product support, user accounts, real-time monitoring, predicting churn.

## 4. Principles (non-negotiable)

| ID | Principle | Enforced by |
|---|---|---|
| P1 | The AI sorts, code counts | All counts, ranks and trends computed in Python |
| P2 | Quotes are copied, not generated | LLM returns review ID; code copies text; excerpt verified as substring |
| P3 | Fee facts come only from official pages | RAG over user-supplied URLs; numbers checked against chunk text |
| P4 | Human approves the exact payload | SHA-256 hash, typed `APPROVE`, hash re-check before each write |
| P5 | No send capability exists | n8n has Create Draft only; no tool name contains "send" |
| P6 | No personal data | Reviewer names dropped at collection; checks script scans for emails/phones |
| P7 | Secrets never in repo | `.env` and Streamlit secrets only |

## 5. Functional requirements

### 5.1 Review intelligence (assignment Step 1)
- FR1: Collect Play Store reviews for `com.openai.chatgpt` (India, English), newest first, up to 12 weeks back. Keep `review_id, date, rating, text, week_start`. Drop names, blanks, reviews under 5 words, duplicates.
- FR2: Save full cleaned CSV and a balanced CSV (max 200 reviews per week).
- FR3: LLM proposes at most 5 themes from a mixed sample (angry, neutral, happy). Code rejects more than 5.
- FR4: LLM assigns each review to exactly one theme, in cached batches.
- FR5: Code counts reviews per theme and 1-2 star reviews per theme; ranks top 3 by the 1-2 star count. Tie-break rule is written in config before results are seen: higher share of 1-2 star reviews wins, then alphabetical.
- FR6: For each top theme the LLM returns a review ID; code copies the exact text (excerpt of 10-25 words verified as a verbatim substring).
- FR7: Fee detection: filter money-related reviews, LLM labels each `confused | complaint_only | praise | unrelated` plus one fee topic from a closed list; code counts. The identified fee issue is the topic with most `confused` reviews.
- FR8 (should): code computes last-4-weeks vs previous-4-weeks trend per top theme and a count of voice-related reviews (Milestone 1 lens).

### 5.2 Weekly Product Pulse (Step 2)
- FR9: At most 250 words. Sections: Summary of top themes, Supporting user quotes, Key observation, 3 action ideas.
- FR10: Code writes title, theme names, counts and trends; LLM writes only sentences and actions. LLM may not output digits for counts (code inserts them).
- FR11: Code counts words and requests a rewrite up to 3 times if over 250.
- FR12: Each action idea must reference something specific in a theme quote.

### 5.3 Fee Explainer (Step 3)
- FR13: User lists 4-6 official source URLs in `config/sources.yaml`. The app downloads each as plain text and records the fetch date. No URL is generated by AI.
- FR14: Chunk, index (BM25) and retrieve top chunks for the identified fee issue.
- FR15: LLM writes at most 6 neutral, facts-only bullets, each citing a source ID.
- FR16: Code validates: bullet count, citation exists, every number appears in the cited chunk, no opinion words (cheap, unfair, expensive, ripoff, etc.).
- FR17: A second LLM call fact-checks each bullet against only its cited chunk. Rejected bullets are rewritten once; if fewer than 4 bullets survive, mark the explainer "needs human review" and block publishing.
- FR18: Append 2 official source links and `Last checked: <YYYY-MM-DD>`.

### 5.4 MCP publishing with approval (Required MCP Actions)
- FR19: n8n workflow exposes an MCP server with exactly three tools: `append_to_doc`, `read_doc`, `create_email_draft`.
- FR20: Approval screen shows the full Doc entry and full email draft, plus the payload hash. User must type `APPROVE` (capitals). Reject asks for a reason and writes nothing.
- FR21: After approval, in fixed order: read_doc (duplicate check) then hash re-check then append_to_doc then read_doc (verify) then hash re-check then create_email_draft. The app calls tools directly; no LLM agent chooses tools.
- FR22: Doc entry JSON contains exactly: `date, top_themes, weekly_pulse, identified_fee_issue, explanation_bullets, source_links`.
- FR23: Email subject: `Weekly Product Pulse + Customer Clarification - <fee issue> - <week>`. Body: pulse, then fee explanation as a reusable support snippet. Draft only, no auto-send.
- FR24: Every step is logged to `outputs/publish_log.jsonl`. A failed run can resume without creating a duplicate entry.

### 5.5 UI and verification
- FR25: Streamlit app with pages: Overview, Insights, Weekly Pulse, Fee Explainer, Approve and Publish, Checks, About.
- FR26: Deployed app runs in demo mode (cached results). Approve page is password-protected.
- FR27: `make checks` runs rule-based tests without any LLM and writes `outputs/checks_report.md`.

## 6. Non-functional requirements

| Area | Requirement |
|---|---|
| Reproducibility | All LLM answers cached by hash of (prompt + model); rerun costs nothing |
| Rate limits | Batches of about 25 reviews, each review cut to about 300 characters, retry with backoff |
| Cost | Free tiers only (Groq, n8n trial, Streamlit Cloud, Google) |
| Security | Bearer token on MCP; secrets in `.env` or Streamlit secrets; `.env` in `.gitignore` from first commit |
| Privacy | No reviewer names or any PII stored or published |
| Performance | Cached full run under 30 seconds; first full run may take several minutes |

## 9. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| LLM miscounts or invents numbers | Wrong insights | Code counts; LLM forbidden from numbers |
| Paraphrased "quotes" | Fake evidence | ID-only quotes, substring verification |
| Complaint mistaken for confusion | Wrong fix (FAQ for a price issue) | Separate `confused` vs `complaint_only` labels |
| Scraped pricing tables collapse | Wrong fee facts | Ban rate numbers in exchange/segment-style bullets; cite page wording; fact-checker |
| Official page changes or blocks download | Stale/empty corpus | Save fetch date; manual-paste fallback; Last checked shown |
| Groq rate limit | Pipeline stalls | Small batches, backoff, cache |
| MCP connection issues (URL type, auth) | Cannot publish | Connection test first; fall back between streamable HTTP and SSE client |
| n8n trial expires after 14 days | Lose publish tools | Start n8n late; export workflow JSON to repo (without credentials) |
| Public app lets strangers write to Doc | Abuse | Approve page password; demo mode; Doc ID fixed in n8n |
| Fee found in data is not covered by official pages | Cannot ground explainer | Choose sources after Phase E; if no official source supports it, pick next-best confused topic |
